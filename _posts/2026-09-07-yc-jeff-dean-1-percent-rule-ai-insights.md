# Jeff Dean 的「1% 法则」与 AI 基础设施的终局思考

*从 YC 访谈到 Google 论文的 6 个洞察*

2026 年 7 月，Jeff Dean 在 Y Combinator Startup School 做了一场近一小时的分享。他反复谈到推理硬件、能耗、数据搬运、context engineering、long-running Agent、自动化实验系统，以及创业公司如何避免被通用模型正面碾压。

但最让我印象深刻的不是任何一个技术细节，而是一句朴素的判断——

> **AI 项目 99% 的工作是工程，不是模型。**

这句话和大多数人的认知完全相反。外行觉得 AI = 模型，内行知道 AI = 基础设施。而这个认知差，恰好就是技术人的机会。

![Jeff Dean 的 1% 法则：AI 冰山](/assets/images/fig37-1-percent-rule.svg)
*用户看到的只是冰山尖上的"模型"。水面下的 99% —— 意图路由、语义层、校验器、血缘追踪、成本核算、安全沙箱 —— 才是系统能在生产环境跑起来的原因。*

---

## 洞察 1：1% 法则 — 模型只是冰山尖

Google 内部有一篇广为流传的论文叫《Hidden Technical Debt in Machine Learning Systems》（2015），里面有一张经典的图：ML 系统里，模型训练代码只占中间那个小方块，周围包着的是数据收集、特征提取、数据验证、机器资源管理、模型服务、监控、配置管理……

Jeff Dean 在 YC 的分享把这个观察推到了极致：在 Google 的实际生产系统里，模型相关的代码不到整体的 1%。剩下的 99% 是：

- **数据管道和清洗**：数据质量决定模型质量的上限
- **特征工程和语义层**：把业务概念翻译成模型能理解的信号
- **Serving 基础设施**：延迟、吞吐、并发、缓存
- **监控和评估**：怎么知道模型在变好还是变差
- **版本管理和回滚**：出了问题能不能秒级回退
- **成本控制**：GPU/TPU 的钱烧在哪里，ROI 如何

### 映射到 LLM 应用

这个规律在大模型应用时代不仅没有失效，反而更加极端。

以一个企业级 AI 数据看板为例：用户输入一句自然语言，系统返回一个交互式图表。"调用 LLM 生成查询"这一步确实只有几十行代码。但围绕它的工程量是：

| 层 | 做什么 | 为什么必须做 |
|---|---|---|
| 意图路由 | 判断用户想干什么（查数据？改图表？闲聊？） | 否则 LLM 会把"删掉这条记录"理解成"删掉这张图表" |
| 语义层 | 把用户的"合同数"映射到正确的数据库字段和筛选条件 | 否则 LLM 会猜错字段名（幻觉率 35%） |
| 结构化输出 | 强制 LLM 输出符合 Pydantic schema 的 JSON | 否则你会收到带 markdown 代码块的"JSON" |
| 多级校验 | 6 道质量门检查字段映射、图表类型、MQL 安全性 | 否则用户看到空白图表或错误数据 |
| 血缘追踪 | 每次 LLM 调用记录 token 数、延迟、成本、关联 ID | 否则出了问题你不知道哪里错了 |
| 安全沙箱 | K8s 隔离执行用户上传的代码 | 否则一个恶意脚本能瘫痪整个平台 |

LLM 调用 = 1%。上面这些 = 99%。这个比例不是夸张，是真实的代码行数统计。

### 对技术人的启示

如果你只会调 API（`openai.chat.completions.create()`），你做的是那 1%。如果你能设计意图路由、搭建语义层、建观测系统、做安全隔离，你做的是那 99%。

**1% 的人在做模型研究，99% 的岗位在做工程。** 这就是为什么"AI 架构师"比"算法研究员"的岗位缺口更大。

## 洞察 2：TPU 的启示 — 专用化是终极优化

Google 为什么要自己做 TPU（Tensor Processing Unit），而不是直接用 NVIDIA GPU？

2017 年 Google 发表了那篇经典的 TPU 论文（*In-Datacenter Performance Analysis of a Tensor Processing Unit*），核心数据是：在推理场景下，TPU 的性能/瓦特比是同期 GPU 的 30-80 倍。原因很简单：GPU 是通用计算硬件，为了兼容游戏、科学计算、图形渲染而保留了大量灵活性；TPU 只做矩阵乘法和低精度运算，把所有晶体管都用在了一件事上。

### 映射到 LLM 应用架构

同样的逻辑：通用 LLM（GPT-4、Claude、GLM-4）是"通用 GPU"——它什么都能做，但在你的具体场景里效率不是最优的。

给 LLM 加约束 = 为你的场景打造"TPU"：

| 通用方式（"GPU"） | 专用化方式（"TPU"） | 效果 |
|---|---|---|
| LLM 面对原始数据库表 | LLM 面对语义视图（boolean labels） | 幻觉率 35% → 18% |
| LLM 自由生成 JSON | Pydantic schema 约束输出 | 格式错误率 15% → 0% |
| LLM 从零写查询 | 编译器把语义计划翻译成 MQL | 执行层零幻觉 |
| LLM 判断所有意图 | 向量短路 + LLM fallback | 37% 请求省掉 LLM 调用 |

每一层约束都是在"削减通用性，换取领域准确性"。这和 TPU 削减通用计算能力、换取推理吞吐量是同一种工程哲学。

Jeff Dean 在 YC 的分享里专门提到：未来的 AI 系统不会是"一个大模型解决所有问题"，而是"一组专用化的模型 + 工程系统协同工作"。这和我们在企业级 AI 平台上看到的趋势完全一致。

## 洞察 3：AlphaChip — AI 设计 AI 的硬件

2020 年，Google 发表了 AlphaChip（当时叫"A Graph Placement Methodology for Fast Chip Design"）。核心能力：用强化学习做芯片布局（macro placement），在几小时内生成超越人类工程师的布局方案。

这项技术已经被用在多代 Google TPU 的设计中。2024 年正式命名为 AlphaChip 并开源。DeepMind 的描述是：

> "AlphaChip generates superhuman or comparable chip layouts in hours, rather than taking weeks or months of human effort."

### AI 递归改进自身

这是一个值得反复品味的递归结构：

```
AlphaChip（AI）设计 TPU（硬件）
  → TPU 加速训练 AlphaChip 的下一代模型
    → 更强的 AlphaChip 设计更好的 TPU
      → ...
```

这不是科幻——这是 Google 正在走的路。Jeff Dean 在 YC 访谈里明确说，他相信 AI 系统能够在越来越多的领域实现"自我改进循环"。

### 映射到应用层

在应用层，我们已经在做一种低配版的"递归改进"：

- AI 生成一条数据查询
- 人类审核这条查询是否正确
- 正确的查询进入 Example Store（范例库）
- Example Store 里的范例成为下一次 AI 生成的 few-shot 参考
- AI 因此生成更好的查询
- 更好的查询被审核后又进入 Example Store
- 循环……

区别在于：AlphaChip 的循环是 AI 自己闭环；我们的循环有人类审核这一环。

我个人认为，在企业级应用中，**有人类审核的递归改进比纯 AI 递归更安全也更务实。** "AI + 人类闭环"不是因为 AI 不够强，而是因为企业场景下错误答案的成本太高——一个错误的财务数据图表可能导致错误的商业决策。

## 洞察 4：AlphaEvolve — Agent 不只是使用工具，还能创造工具

2025 年 5 月，DeepMind 发布了 AlphaEvolve —— 一个基于 Gemini 的编码 Agent，专门用来发现和优化算法。

核心架构很巧妙：
- **Gemini Flash**（快速模型）负责广度——大量生成候选算法
- **Gemini Pro**（强力模型）负责深度——对有潜力的候选做精细改进
- **自动化评估器**验证正确性
- **进化框架**保留最优解，淘汰劣解

AlphaEvolve 已经在多个领域取得了突破：更快的矩阵乘法算法、Google 数据中心效率优化、芯片设计流程改进——甚至改进了训练 AlphaEvolve 自身底层 LLM 的过程。

2026 年 7 月，AlphaEvolve 在 Google Cloud 上对所有人开放。

### 当 Agent 能创造工具

当前大多数 AI Agent（包括绝大多数企业级部署）还停留在"使用预定义工具做预定义任务"的阶段。你给 Agent 一把锤子和一把螺丝刀，它能决定什么时候用哪个，但它不能自己造一把新工具。

AlphaEvolve 代表了下一个阶段：Agent 不仅使用工具，还能**创造新工具**。

回到实际场景：一个 SkillHub（技能市场）允许用户发布新的 AI 技能。今天，技能是人写的。明天的可能性是：

```
Agent 发现：用户频繁要求"把报表导出为 Excel"
  → 但当前没有这个技能
  → Agent 向 SkillHub 提交一个"导出 Excel"技能的草案
  → 安全扫描 + 人类审核 → 发布
  → 下次用户再要求时，这个技能已经可用了
```

这不是幻想——技术组件已经存在（代码生成、沙箱执行、安全扫描、发布审核）。缺的只是把它们串起来的"自主发现需求"能力。

## 洞察 5：知识蒸馏 — 大模型的"教学"本能

2015 年 Hinton 等人发表了《Distilling the Knowledge in a Neural Network》，提出知识蒸馏（Knowledge Distillation）：用大模型的"软标签"（概率分布）训练小模型，效果远好于直接用硬标签（0/1）。

核心直觉：大模型不仅知道"这张图片是猫"，还知道"这张图片 80% 像猫、15% 像豹、3% 像虎、2% 像其他"。这个概率分布里包含了丰富的"暗知识"（dark knowledge）——哪些类别容易混淆、特征之间的关系是什么。小模型从这些软标签里学到的远比从硬标签（"猫=1，其他=0"）学到的多。

### 应用层的"蒸馏"

在 LLM 应用中，知识蒸馏的思想无处不在：

**记忆蒸馏**：大模型从对话中提取用户画像（"这个用户关注社保业务"、"偏好用柱状图"），存为结构化的语义记忆。下次对话时，注入这些蒸馏后的记忆——不需要每次都重新理解整段对话历史。注入的成本极低（几条文本），但信息密度极高。

**语义蒸馏**：把复杂的业务逻辑蒸馏成简单的布尔值。数据库里的 `bill_status` 有 5 种取值、`pay_status` 有 3 种取值、`invoice_status` 有 4 种取值。蒸馏后变成 `is_confirmed: true/false`、`is_paid: true/false`、`is_invoiced: true/false`。LLM 面对 3 个布尔值的决策质量远高于面对 12 种枚举组合。

**范例蒸馏**：example store 里的每一条人类审核过的 (问题, 查询) 对，本质上是把"一个领域专家审核查询时的隐性知识"蒸馏成了一条可复用的范例。新的 AI 调用不需要重新具备领域专家的全部知识，只需要"看到前人审核过的相似案例"就能做得更好。

Hinton 的洞察放到 2026 年来看，比 2015 年更有价值：**在大模型能力溢出的时代，蒸馏（把大模型的能力浓缩成小而精的信号）是最重要的工程技能之一。**

## 洞察 6：YC 的 AI 创业趋势 — 壁垒不在模型

从 YC 2024-2026 年的 AI 项目批次来看，一个趋势非常明显：

**Vertical AI（垂直领域 AI）远比 Horizontal AI（通用 AI）受欢迎。**

原因很简单：通用 AI 是 OpenAI、Google、Anthropic、Meta 的战场。你作为创业公司，不可能在"做一个更好的 ChatGPT"上赢过它们。但你可以在"做一个更好的 [某垂直行业] AI 助手"上赢——因为你有它们没有的东西：

- **领域数据飞轮**：行业里的审核过的查询范例、业务术语映射、异常模式
- **领域 know-how**：知道"合同数"在这个行业指的是什么条件下的什么数据
- **客户信任**：客户愿意把数据交给你是因为你懂他们的业务，不是因为你的模型更强

Jeff Dean 在 YC 也明确说了：创业公司应该关注那些**大模型不擅长、需要领域深度**的问题。通用模型越强，"领域专用化"的价值反而越高——因为你不是在和模型竞争，你是在**给模型加上它缺少的领域知识**。

### 1% Rule 的创业版

```
你的差异化 ≠ 你用的模型（GPT-4 还是 Claude，大家都用一样的）
你的差异化 = 你围绕模型建的那 99%：
  - 你的语义层（领域术语怎么映射到数据）
  - 你的验证系统（怎么确保答案正确）
  - 你的闭环（用户反馈怎么变成 AI 改进）
  - 你的安全基线（怎么在企业环境里合规运行）
```

## 写在最后

Jeff Dean 8 月份从 Google 离职，创立了 Discovery Loop —— 一家专注于"自动化科学发现"的公司。他说，运行成千上万个自动化循环可以在科学、生物、芯片设计甚至 AI 模型改进等多个领域解锁突破性进展。

从 TPU 到 AlphaChip，从 AlphaEvolve 到 Discovery Loop，Jeff Dean 用整个职业生涯证明了一件事：

**真正推动 AI 进步的，不是更大的模型，而是更好的基础设施。**

模型是天才科学家。基础设施是让天才能够专注工作的实验室、仪器、安全措施和后勤保障。没有后者，前者再聪明也只能在纸上演算。

对于技术人来说，这是个好消息。因为基础设施 = 工程能力 = 我们的主场。

> **"The boring stuff is what makes AI work."**
> — Jeff Dean, YC Startup School 2026

用户看到的是一个智能对话框。看不到的是背后的语义层、意图路由、6-gate 校验、8-table 血缘、K8s 沙箱、NetworkPolicy —— 这些"无聊的 99%"才是系统的灵魂。

而恰恰是这些无聊的东西，构成了最坚固的护城河。
